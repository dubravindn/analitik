# Forecast Data Audit — Hermes

**Дата:** 2026-08-13  
**Ветка:** `etap-1-vizual`  
**Скрипт:** `scripts/audit_forecast_data.py`  
**Статус:** зафиксированный, базовый для `forecast_data.py`

---

## 1. Контекст

Аудит проводился перед реализацией новой модели прогнозирования, чтобы
оценить, насколько историческим данным можно доверять при расчёте спроса
и детекции stockout.

Охват: все SKU СРЕЗКА, все склады, период Aug 4–13 2026.
Проверялось: согласованность снимков остатков (`stock_snapshot`) с
задокументированными движениями (продажи, поставки, перемещения,
оприходования, списания).

---

## 2. Структура данных

### Используемые таблицы

| Таблица | Содержание | Timestamp |
|---|---|---|
| `stock_snapshot` | Остатки по товару×склад×день | `synced_at` (время записи ETL, ≠ время снимка) |
| `sales_by_product_day` | Продажи агрегировано за день | нет (только `day`) |
| `sales_doc` | Документы продаж | `moment` (до 64 документов/день/склад) |
| `supply_doc` / `supply_item` | Поставки | `moment` |
| `enter_doc` / `enter_item` | Оприходования | `moment` (ненадёжен, см. §4.4) |
| `loss_doc` / `loss_item` | Списания | `moment` |
| `move_doc` / `move_item` | Внутренние перемещения | `moment` |

### Важные ограничения схемы

- `sales_by_product_day` — **нет timestamp** индивидуальных продаж. Только агрегат за день.
- `sales_doc` — нет связки с `product_id` на уровне позиций (только `store_id`, `day`).
- `supply_item`, `enter_item`, `loss_item` — **нет `store_id`**; склад берётся через JOIN с `*_doc`.
- `stock_snapshot.synced_at` — время записи ETL, **не** время снятия остатков в МойСклад.

## 3. Результаты balance-проверки

### 3.1 Исходная calendar-day методология

Аудит сравнивал изменение остатка между последовательными снимками с суммой
движений за тот же **календарный день**.

```
balance_error = (stock_d1 - stock_d0) - (supply + enter + move_in - sales - move_out - loss)
```

**Результат:** 158 / 357 проверок = **44.4% failures**.

Это число создавало ложное впечатление системной проблемы с данными.

### 3.2 Ошибка методологии №1 — calendar-day vs timestamp-window

Снимки `stock_snapshot` берутся в ~05:00 UTC (08:00 МСК). Движения товара
происходят в течение дня. Например, поставка Aug 7 в 12:11 UTC
физически попадает **в окно T(Aug7 snap) → T(Aug8 snap)**, но
calendar-day методология относила её к окну Aug6→Aug7.

Это систематически смещало знак ошибки:
- День поставки показывал отрицательный balance_error (товар «исчез»)
- Следующий день показывал положительный (товар «появился» без причины)

**Исправление:** использовать timestamp-окно [T0, T1] где T0, T1 — `synced_at`
соответствующих снимков. Движения включаются если `T0 < moment <= T1`.

### 3.3 Ошибка методологии №2 — неправильный день продаж

`sales_by_product_day` не имеет timestamp. Исходная formula V1 использовала:

```
продажи дней: d_start+1 ... d_end  (включительно)
```

Физически верно: магазин открывается в 09:00 МСК (06:00 UTC), снимок берётся
в 05:00 UTC. Поэтому продажи дня D0 происходят **после** снимка T0, а продажи
дня D1 происходят **после** снимка T1. Правильная формула V2:

```
продажи дней: d_start ... d_end-1  (d0 включён, d1 исключён)
```

Для типичного 1-дневного окна это означало полную замену: V1 включала продажи
d1, V2 включает продажи d0 — разные числа.

### 3.4 Итоговая таблица методологий

| Методология | Failures | % | Median \|err\| |
|---|---|---|---|
| Calendar-day (оригинал) | 158/158 | 100.0% | 24.5 |
| Hybrid V1 (timestamp движений, неправильный день продаж) | 106/158 | 67.1% | 8.5 |
| **Hybrid V2 (timestamp движений, правильный день продаж)** | **34/158** | **21.5%** | — |
| — из них: частичный ETL Aug8/Aug12 | 10 | 6.3% | — |
| **Истинные unexplained residuals** | **24** | **15.2%** | 25 |

## 4. Специфические находки

### 4.1 Частичный ETL — Aug 8 и Aug 12

ETL фиксирует снимки per-store без глобальной транзакции. При прерывании
процесса только часть складов получает снимок.

| Дата | Склад | SKU в снимке | Типичное кол-во | Покрытие |
|---|---|---|---|---|
| 2026-08-08 | База Воровского 107/1 | ~102 | ~152 | ~67% |
| 2026-08-12 | Розница Воровского 107/1 | ~21 | ~65 | ~33% |

Любой balance-check с одним из этих дней как endpoint **не является надёжным**
для затронутых продуктов.

### 4.2 `enter_doc` — не включался в старую формулу прогноза

4 документа, 167 позиций, **4773 единицы** суммарно за Aug 7–11.
Это существенный объём. Старые расчёты stockout могли интерпретировать
эти периоды как дефицит, хотя на самом деле происходило оприходование.

Выводы о stockout и дефиците из периодов до этого аудита следует считать
**предварительными** — до проверки через новый data layer.

### 4.3 `SYNC_VARIABLE` — synced_at ≠ время снимка

`stock_snapshot.synced_at` проставляется как `now()` в момент INSERT/UPDATE ETL.
Это не момент, когда МойСклад снял остатки. Реальное время снимка в МойСклад
неизвестно из данных в БД.

Следствие: при временном анализе нужно использовать `synced_at` как **нижнюю
границу** времени записи, понимая, что сам снимок мог быть немного раньше.

### 4.4 `enter_doc.moment` — ненадёжен как timestamp события

Обнаружен случай: `enter_doc.moment = 04:01 UTC Aug7`, но снимок `Aug7 05:00 UTC`
не содержит этих единиц в остатке. Вероятная причина: `moment` задаётся
пользователем вручную как бизнес-дата, тогда как фактическое проведение
документа в МойСклад произошло позже.

Следствие: `enter_doc.moment` нельзя использовать как точный timestamp события
для timestamp-based balance check.

### 4.5 24 unexplained residuals — детали

Чистые случаи (без частичного ETL), где V2 balance не закрывается:

| Диапазон \|err\| | Кол-во |
|---|---|
| 1–5 | 4 |
| 5–25 | 9 |
| 25–80 | 11 |

Большинство сосредоточено в **База Воровского 107/1**. Ошибки часто кратны 25
(типичный размер упаковки в цветочном ассортименте).

**Возможные причины (НЕ установленные факты):**
- незадокументированное физическое движение
- отсутствующий тип документа в ETL
- изменение документов задним числом в МойСклад
- временная несогласованность между snapshot-временем и моментом документа
- ошибки ввода данных

Все 24 случая остаются **UNEXPLAINED** до дополнительного расследования.

### 4.6 `sales_by_product_day` — ограничения для анализа доступности

Таблица содержит только дневные агрегаты. Из неё **невозможно**:
- определить, в какое время суток происходила продажа
- установить, продавался ли товар из остатка или из резерва
- подтвердить, что отсутствие строки = отсутствие продаж (vs. отсутствие SKU в ассортименте магазина)

## 5. Классификация качества данных

Вместо бинарного DATA_OK / DATA_NOT_OK для каждого `product_id × store_id × day`
вводятся гранулярные признаки. Это входные данные для `forecast_data.py`.

| Признак | Тип | Значение |
|---|---|---|
| `snapshot_present` | bool | есть ли строка в stock_snapshot |
| `snapshot_volume_anomaly` | bool | день с частичным ETL (Aug8, Aug12 + будущие) |
| `balance_ok` | bool | V2 balance закрывается (только если оба снимка присутствуют) |
| `balance_abs_error` | float | \|err\| при V2 check, NULL если нет снимка |
| `sync_window_known` | bool | synced_at доступен для обоих endpoints |
| `sales_day_available` | bool | есть хотя бы 1 строка в sales_by_product_day за период |
| `unexplained_movement` | bool | balance_ok=False без известной причины (enter_doc, частичный ETL) |
| `data_quality_score` | float 0–1 | агрегированная оценка (алгоритм в forecast_data.py) |

## 6. Состояния доступности для прогноза

Три состояния для `product_id × store_id × day`:

| Состояние | Критерий |
|---|---|
| `IN_STOCK_CONFIRMED` | snapshot_present=True И balance_ok=True И stock_qty>0 |
| `STOCKOUT_LIKELY` | snapshot отсутствует ИЛИ stock_qty=0, при выполнении паттерна (см. ниже) |
| `AVAILABILITY_UNKNOWN` | всё остальное |

**Паттерн для `STOCKOUT_LIKELY`** (все условия одновременно):
1. В предшествующем подтверждённом снимке остаток был низким (< 10% от max за период)
2. Строка отсутствует или stock_qty = 0
3. Продажи за период равны 0 или отсутствуют
4. После следующей поставки/перемещения строка восстанавливается
5. День не является аномальным (snapshot_volume_anomaly = False)

Пока паттерн не проверен на истории — по умолчанию `AVAILABILITY_UNKNOWN`
предпочтительнее ложного `STOCKOUT_LIKELY`.

---

## 7. Что НЕ делать на основе этого аудита

- Не экстраполировать спрос через AVAILABILITY_UNKNOWN дни (нельзя считать их
  ни наличием, ни stockout)
- Не считать `enter_doc.moment` надёжным timestamp для точного boundary-анализа
- Не использовать `synced_at` как время снимка МойСклад
- Не интерпретировать 15.2% unexplained residuals как «данные сломаны» — это
  верхняя граница проблемы, реальное влияние на спрос-прогноз требует отдельной оценки
- Не считать старые выводы о stockout/дефиците достоверными без перепроверки
  через новый data layer
